# 05 — Data Solutions for Me: Expectation Transparency, Event-Driven Change History, and Project Accountability

**Source repo:** [andredavisme/data-solutions-for-me](https://github.com/andredavisme/data-solutions-for-me)  
**Completed:** 2026-06-10  
**Theme:** A project hub platform built around the transparent, timestamped history of expectations, deviations, and adaptations. Every concept in this system — event promotion, manual annotation, context isolation, realtime visibility, and portfolio-readiness — maps directly onto the principles that govern information distribution in any business that manages commitments to customers, vendors, and internal teams.

---

## 1. The Three Concepts That Should Drive Every Project Record

The platform is built on three explicitly defined concepts:

- **Expectation**: A documented commitment about scope, timing, budget, or outcomes.
- **Deviation**: A meaningful divergence from an expectation (slip, surprise, risk materialized).
- **Adaptation**: A conscious response to a deviation (re-scoping, resequencing, new approach).

These three are recorded as timestamped events and visualized on a timeline. Everything else in the system exists to support the accurate, queryable history of these three things.

### Business Takeaway
**Every business commitment generates a data obligation.** When a business tells a customer a delivery date, quotes a price, or commits to a scope of service, that commitment becomes an expectation on record. When reality diverges from that expectation, the divergence is a deviation. When the business responds — adjusting the date, revising the scope, offering a credit — that is an adaptation. Businesses that record all three have an auditable, honest account of what was promised, what changed, and why. Businesses that don't have disputes.

**Applied to RFQ/service workflows:**
- Every quote, order confirmation, and delivery promise is an expectation. Record it as such, with a timestamp and the values committed.
- When any of those values changes — delivery date slips, price changes, scope expands — record the deviation explicitly, with a timestamp, the original value, the new value, and the reason.
- When you respond to a deviation — issuing a revised quote, adjusting the schedule, notifying the customer — record the adaptation, linking it to the deviation it addresses.
- Do not overwrite the original expectation with the revised one. The history of changes is as important as the current state.

## 2. Two Event Sources, One Timeline: Automatic and Manual

The platform distinguishes two types of events:

- **Automatic events**: Generated by database triggers watching for changes to data tables. These capture system-level facts: what was inserted, updated, or deleted, and when.
- **Manual events**: Authored by humans to document expectations, deviations, or adaptations in narrative form.

Manual events can reference automatic events via `related_event_ids`, effectively annotating system-level signals with human interpretation. Both appear on the same timeline.

The visual distinction is explicit: automatic events are circles sitting on the axis line; manual events are squares positioned above it.

### Business Takeaway
**System-generated data and human-authored context are both required for a complete record.** A database log shows that an order was updated on a given date — but it does not explain why. A human narrative explains why — but without the system log, it cannot be tied to a specific data change. Linking the two produces a record that is both verifiable and interpretable.

**Applied to RFQ/service workflows:**
- Build two layers into every significant business event: the system record (what changed, when, in what system) and the human context (why it changed, what was communicated to the customer, what the resolution was).
- When a sales rep changes a delivery date in the order management system, that change should automatically generate a system event. The rep should then author a brief annotation: the reason, what the customer was told, and whether further action is required.
- Both layers should be linked: the annotation should reference the system event it explains.
- Reports built only on system data will be accurate but uninterpretable. Reports built only on human notes will be interpretable but unverifiable. You need both.

## 3. Raw Events vs. Normalized Events: The Two-Stage Pipeline

The architecture separates raw instrumentation (`monitor_events`) from normalized, project-scoped records (`project_events`). Raw events capture every trigger-fired change; the `transform-monitor-events` Edge Function promotes them into the canonical event store, mapping database operations to business concepts:

| Database Operation | Promoted Event Kind |
|-------------------|--------------------|
| INSERT | expectation |
| UPDATE (status change) | deviation |
| UPDATE (no status change) | adaptation |
| DELETE | delete |

This promotion logic encodes a business interpretation: adding a record is setting an expectation; changing a status is a meaningful deviation; other updates are adaptations.

### Business Takeaway
**Raw operational data must be translated into business-meaningful events before it can be used for accountability.** A database INSERT is not inherently meaningful to a customer-facing team. "A new delivery commitment was recorded" is. The translation layer — from technical event to business event — is where data becomes usable for communication, reporting, and accountability.

**Applied to RFQ/service workflows:**
- Design a promotion layer for every high-volume operational data source: what do the raw events mean in business terms?
- Status changes deserve special treatment because they represent the most significant business events: an order moving from "quoted" to "confirmed," a shipment moving from "in transit" to "delayed," a request moving from "submitted" to "responded."
- The promotion rules should be explicit, documented, and stable. Every time a status change is promoted to "deviation," the team should know exactly what that means and what response is expected.
- Automate the promotion where the mapping is deterministic; require human authorship where interpretation is needed.

## 4. Context Isolation: Production, Development, and Test Are Not the Same

Every event in the system carries a `context` field: `production`, `development`, or `test`. Production events are the canonical record. Development and test events are visible but rendered with a dashed outline and labeled. They can be filtered out. The rule is explicit: never write `development` or `test` rows to production without intent.

### Business Takeaway
**Data generated by testing, training, or development activity must never contaminate the canonical operational record.** When a business is testing a new quoting workflow, the test quotes should not appear in the reporting that drives inventory planning, performance metrics, or customer communications. Contamination of production data with test data is one of the most common and most damaging forms of data quality failure in small businesses.

**Applied to RFQ/service workflows:**
- Tag every record in every system with its context: is this a real customer quote, a test entry, a training record, or a demonstration?
- Build filters and reports that exclude non-production records by default. Non-production data should require explicit opt-in to view, not opt-out to hide.
- When onboarding new team members or testing system changes, use a dedicated test environment or explicitly-tagged test records — never the live production system without tagging.
- Audit your current records for context contamination: are there test records, demo quotes, or training entries mixed into your production data? If so, clean them out and tag all future non-production records.

## 5. Realtime Visibility: The Value of Live-Updating State

The timeline updates live via Supabase Realtime — no page refresh needed. When a new event is written, it appears on the timeline immediately. A live status badge shows connection state. A flash animation signals a new arrival.

This is not a cosmetic feature. It is the operational principle that the current state of any project should be visible without manual refresh, polling, or asking someone for an update.

### Business Takeaway
**Status that requires a phone call or email to obtain is status that will be requested less often than it should be.** Customer service reps who must ask a warehouse manager for an order status will ask less often and wait longer than if they can see it directly. Customers who must call for delivery updates will be less satisfied than those who receive automatic notifications. Realtime visibility reduces the communication overhead of staying current.

**Applied to RFQ/service workflows:**
- Identify every status in your RFQ and order workflow that is currently obtained by asking someone: order status, delivery ETA, inventory availability, quote approval. Each one is a candidate for real-time data visibility.
- For each, determine whether the bottleneck is a system capability gap (the data exists but isn't exposed) or a process gap (the data isn't being recorded at all). These require different solutions.
- Customer-facing status visibility — a tracking page, an automated status email, a portal — reduces inbound inquiry volume and improves customer confidence.
- Internal real-time dashboards reduce the coordination overhead between departments: customer service, warehouse, logistics, and sales can all see the same current state without asking each other.

## 6. Annotation: Linking System Events to Human Interpretation

When a user selects an automatic event, they see an "Annotate this event" button. This opens a drawer to author a manual event linked to the automatic one. The annotation is a narrative record: kind, context, author, summary, and full narrative. Once created, it appears in a "Linked annotations" panel on the automatic event's detail card.

Annotations are editable and deletable. Every mutation propagates to the timeline in real time.

### Business Takeaway
**Every system event that matters to a customer, vendor, or internal stakeholder deserves a human annotation.** The system event is the fact. The annotation is the context: why it happened, what it means, who was notified, and what happens next. Without annotations, operational data is a list of events. With annotations, it is an account.

**Applied to RFQ/service workflows:**
- Build annotation into your operational workflow: every time a significant status changes (order delayed, delivery rescheduled, price revised), require the responsible person to author a brief annotation: cause, action taken, customer communication status.
- Annotations should be associated with the specific record they explain, not stored in a general notes field or communicated only by email.
- Make annotations visible to everyone who needs to work with the record — not just the person who wrote them.
- The annotation discipline creates an institutional memory that survives personnel changes: the next person to work with the record can see exactly what happened and why.

## 7. Single-Project Hub, Portfolio-Ready Architecture

All events are scoped by `project_id`. The system is designed for a future aggregator hub that can query across multiple project IDs for portfolio timelines, deviation heatmaps, and adaptation-lag metrics — without breaking the single-project hub's self-contained integrity.

The roadmap explicitly names future metrics: time from deviation to adaptation, deviation frequency, and expectation-change distribution.

### Business Takeaway
**Every system you build for a single project, order, or customer should be architected as if it will eventually need to be viewed alongside all the others.** A quoting system that works for one customer but cannot be queried across all customers is not a data system — it is a filing cabinet. The decision to scope by `project_id` is the decision that makes cross-project reporting possible later without rebuilding.

**Applied to RFQ/service workflows:**
- Every record in your RFQ and order management system should be tagged with the entity it belongs to: customer ID, order ID, project ID, contract ID. These are the foreign keys that make aggregate reporting possible.
- Design every report you run today as if you will eventually want to run it across all customers, all time periods, or all product lines. The fields you include now determine the analyses you can run later.
- The three future metrics named in the roadmap (time from deviation to adaptation, deviation frequency, expectation-change distribution) are valuable for any business:
  - **Deviation frequency** = how often do commitments slip? High frequency signals systemic over-promising or under-resourcing.
  - **Time from deviation to adaptation** = how quickly does the business respond when something goes wrong? Long lag times signal communication or decision-making failures.
  - **Expectation-change distribution** = which types of commitments change most often? This identifies which processes need the most improvement.

## 8. Auth Gate Discipline: Transparency Has Boundaries

The platform's auth gate is temporarily disabled due to a JWT configuration issue — and this is explicitly documented with a clear statement of what is bypassed, what remains intact, and how to re-enable it. The scaffolding is present; only the UI gate is bypassed.

This is not a documentation afterthought. It is a model for how to handle temporary security or access exceptions: document the exception, document what is still protected, document how to restore full protection.

### Business Takeaway
**Every access control exception — temporary or permanent — should be documented with the same rigor as the control itself.** "We disabled the approval step temporarily" is not governance. "We disabled the approval step on 2026-05-21 because of X; Y remains in place; to re-enable, do Z" is governance. The difference is accountability.

**Applied to RFQ/service workflows:**
- When an access control, approval step, or data validation is bypassed — even temporarily — document it: what was bypassed, when, why, what compensating controls exist, and how to restore it.
- Temporary exceptions that are not documented become permanent exceptions by default. The undocumented workaround is the control that never gets re-enabled.
- Apply the same discipline to data access: if someone is granted temporary access to a system or data set outside their normal role, document the grant, the scope, the duration, and the removal.

## 9. The Timeline as a Communication Instrument

The project hub's timeline is not just a technical log — it is a communication instrument. It is designed to be shared with collaborators, used in project reviews, and eventually aggregated into portfolio views. The visual treatment (circles for automatic events, squares for manual, dashed outlines for non-production) is designed for human interpretation, not just system correctness.

### Business Takeaway
**A data record that cannot be communicated is a data record that will not be used.** The difference between a database log and a project timeline is that the timeline is designed for human consumption. Businesses that invest only in data storage and not in data presentation produce records that inform only the people who built the system.

**Applied to RFQ/service workflows:**
- For every key data set in your business (order history, customer expectations, delivery performance), design a view that is readable by a non-technical stakeholder in under 60 seconds.
- The expectation-deviation-adaptation framework is a presentation layer, not just a data model. Use it to structure customer communications, vendor reviews, and internal project updates: what did we commit to, what changed, and what did we do about it?
- Build status summaries for recurring touchpoints: weekly order status reports, monthly performance reviews, quarterly vendor scorecards. Each should follow the same structure: expected state vs. actual state, deviations, adaptations.

| Two-stage event pipeline | Raw events promoted to business-meaningful kinds | Translate operational data into accountability language |
| Context isolation | Production / development / test per event | Tag all non-production records; exclude from canonical reporting |
| Realtime visibility | Live timeline, no manual refresh | Status requiring a call is status that won't be checked enough |
| Annotation discipline | Manual events linked to automatic events | Every significant status change deserves a human explanation |
| Portfolio-ready scoping | All events scoped by project_id | Design records today for cross-entity reporting tomorrow |
| Exception documentation | Auth gate bypass documented with restoration steps | Every access control exception must be documented |
